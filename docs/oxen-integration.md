# Интеграция с Oxen Card API

Источник: https://docs.sbx.oxen.finance
(Guide, API Contract, Changelog — читать первоисточник при сомнениях.)

Всё взаимодействие — **только** через `src/server/oxen`. Из бизнес-логики
прямых HTTP-вызовов нет. Причина: их контракт менялся ломающими
изменениями еженедельно (11.09, 17.09, 24.09, 25.09 — после того как
контракт был объявлен финализированным 26.08). Адаптер — наш буфер.

---

## Базовое

- Sandbox: `https://api.sbx.oxen.finance/v1/card`
- Production: адрес выдаётся при go-live
- Авторизация: `Authorization: Bearer <ключ>`, один ключ на всю платформу
- Ответы завёрнуты в конверт, в `_metadata` есть `requestId` —
  **логировать всегда**, это то, с чем обращаются в поддержку

---

## Модель ресурсов

```
client       cl_…    компания (KYB) = один пул залога = один депозитный адрес
cardholder   chd_…   человек под компанией
card         card_…  виртуальная | физическая
counterparty cpt_…   кошелёк в адресной книге компании
deposit      top_…   поступление на депозитный адрес
withdrawal   pwd_…   вывод из залога
event        evt_…   конверт вебхука
transaction  UUID    БЕЗ префикса — id эмитента, не их внутренний id
```

Важно: `transaction.id` — единственный идентификатор без префикса.
Префикса `txn_` не существует, хотя он был в черновике.

---

## Что мы используем, а что нет

**Используем:** cardholders, cards, limits, secrets (реквизиты),
transactions, events, funding (чтение пула).

**Не используем:** создание клиентов через API (KYB проходится лично),
withdrawals (вывод вручную через их админа), counterparties
(пополнение пула вне платформы), физические карты, shipping, disputes
(на старте), **PIN** — карты только виртуальные и живут в кошельке,
PIN у них не запрашивается (`docs/open-decisions.md`, п. 17).

## Ключевые эндпоинты

```
GET  /clients/:id                 компания, депозитный адрес
GET  /clients/:id/funding         пул и spending power  (рейт-лимитится целиком)

POST /clients/:id/cardholders     создать пользователя        🔑 идемпотентный
GET  /cardholders/:id             статус пользователя
GET  /cardholders?client_id=…     список

POST /cardholders/:id/cards       выпустить карту           🔑 идемпотентный
GET  /cards/:id                   карта
PUT  /cards/:id/limit             изменить лимит (АБСОЛЮТНОЕ значение)
POST /cards/:id/freeze            заморозить
POST /cards/:id/unfreeze          разморозить
POST /cards/:id/cancel            отменить (необратимо)

POST /cards/:id/secrets           реквизиты (зашифрованные)
PUT  /cards/:id/pin               установить PIN

GET  /transactions?client_id=…    список (страница до 100)
GET  /transactions/:id            транзакция, в т.ч. declineReason

GET  /events                      догон событий по курсору
POST /webhook-endpoints           регистрация эндпоинта
```

`client_id` — **обязательный** query-параметр на списках cardholders,
cards, transactions, disputes. Заголовок `X-Client-Id` больше не читается.

## Идемпотентность

Заголовок `Idempotency-Key` обязателен на:
- `POST /clients`
- `POST /clients/:id/cardholders`
- `POST /cardholders/:id/cards`
- `POST /clients/:id/withdrawals`

На остальных создающих запросах ключ не принимается.

Ключ генерируем мы, **сохраняем в БД до отправки запроса** вместе с
намерением. Иначе при падении процесса мы не узнаем, был ли выпущен
картхолдер или карта.

## Ретраи — allow-list по коду, не по статусу

У Oxen **нет** правила «5xx можно повторить». Неизвестный код, включая
любой 5xx, повторять нельзя.

Порядок при ошибке:
1. Код в allow-list retryable → повторить, как указано в его правиле.
2. Код не в списке → **остановиться**, перечитать ресурс, если чтение
   существует; иначе — в очередь ручного разбора с `requestId`.

Критично:
- `502 CARD_UNRECORDED` — **никогда не повторять**: повтор выпустит вторую карту.
- `502 PROVIDER_AMBIGUOUS` на activate / freeze / unfreeze / cancel / limit —
  повтор с тем же запросом безопасен.
- `502 PROVIDER_AMBIGUOUS` на создающем запросе — **не повторять**, перечитать.
- `409 LIMIT_UPDATE_IN_PROGRESS` — retryable, но лучше не допускать:
  ставим блокировку на карту у себя.
- `429 PROVIDER_RATE_LIMITED` — подождать, учитывать
  `error.params.retryAfterSeconds`.
- `429 REVEAL_RATE_LIMITED` — исчерпан лимит просмотров реквизитов
  конкретной карты.

## Рейт-лимиты — общие на всю платформу

Не персональная квота: считается по IP и по общему бюджету, разделяемому
всеми партнёрами. Превышение отдаёт **`401`, неотличимый от неверного ключа**.

Следствия:
- Глобальный троттлинг исходящих запросов на нашей стороне.
- `401` **никогда** не повторять в цикле — при троттлинге это усугубит.
- При серии `401` — снизить скорость, поднять флаг в админке,
  обратиться в поддержку с `requestId`.
- Перед ростом нагрузки — предупреждать Oxen.

## События и вебхуки

### Доставка — ОДИН раз, без ретраев

Это самое важное. Если наш эндпоинт лежал — событие потеряно навсегда,
кроме как через догон.

**Догон обязателен с первого дня**, не «добавим потом»:
`GET /events` с курсором, крутится фоновым процессом постоянно.

Нюанс: непустой `nextCursor` означает «запросить ещё раз», а не «есть
ещё события». Подтверждение того, что догнали — пустая страница с
курсором `null`.

### Проверка подписи

1. Взять **сырые байты** тела, до парсинга JSON.
2. Прочитать id события из заголовка `X-Oxen-Event-Id`.
3. Проверить HMAC по сырым байтам.
4. Только после этого парсить.

Next.js по умолчанию парсит тело — на роуте вебхука это нужно отключить
и читать поток как есть.

### Дедупликация

По `evt_…`. Одно и то же событие может прийти и вебхуком, и догоном.
Запись в `OxenEvent` с id как первичным ключом, обработка идемпотентная.

### Событие — уведомление, а не запись

В `data` приходит только разрешённый минимум. Значения там — в
**вокабуляре эмитента в нижнем регистре** (`pending`, `completed`,
`canceled`), а не в UPPER_SNAKE enum REST-API. Не сравнивать значения
события с enum'ами чтения.

Правильный паттерн: событие говорит, **что перечитать**; действуем по
результату чтения.

Отдельно: причина отказа в событиях не приходит — `declineReason`
читается через `GET /transactions/:id`.

### 3-D Secure

`challenge.requested` приходит на обычный вебхук-эндпоинт и несёт
**одноразовый пароль**, `expiryTime`, сумму и мерчанта.
Синхронного релея нет.

- Доставлять пользователю немедленно, приоритетной очередью.
- Показывать вместе с обратным отсчётом до `expiryTime`.
- Событие пушится один раз; пропущенное придёт только догоном, когда
  код уже протух.
- `amount` в этом событии — в минорных единицах ISO 4217,
  **не в сотых долях**, в отличие от других событий.

## Реквизиты карты (secrets)

Схема:

1. Генерируем секрет — 32 hex-символа (16 байт).
2. Шифруем его RSA-OAEP публичным ключом Oxen → `sessionId`.
3. `POST /cards/:id/secrets` с `sessionId`.
4. В ответ — `encryptedPan`, `encryptedCvc`, зашифрованные **нашим**
   секретом.
5. Расшифровываем.

Oxen ключа для расшифровки не имеет — данные проходят через них
непрозрачно.

**Наше решение:** шаги 1, 2 и 5 выполняются **на клиенте**. Сервер
проксирует `sessionId` и шифротекст, открытых данных не видит.
Подробности и обоснование — `docs/security.md`.

Ограничение: просмотр реквизитов и просмотр PIN делят **один общий
бюджет запросов на карту**. UI должен корректно обрабатывать `429`.

## Карты

- `limit` **обязателен** при выпуске. Без него `422`, карта не выпускается.
- Виртуальная карта: `shipping` отправлять нельзя — отказ.
- `displayName` на виртуальной карте никуда не передаётся и ни на что
  не влияет — не отправлять.
- **Перевыпуска нет.** `POST /cards/:id/replace` удалён, отвечает `404`.
  Замена = заморозить/отменить + выпустить новую с правильным остатком.
- `409 CARD_TERMINAL` — операция над отменённой картой. Необратимо.
- `card.updated` несёт только текущий статус (`active`, `locked`,
  `canceled`, где `locked` = `FROZEN` в чтении). Любое другое значение —
  повод перечитать карту.

### Как считается лимит у Oxen

- Счётчик потраченного **переживает любое изменение лимита**.
- Одобренные, но не списанные покупки **считаются**.
- Возвраты и отмены возвращают бюджет.
- Окна **скользящие**: `PER_DAY` = последние 24 часа, не до полуночи.
- **Сброса нет.**
- Пул компании проверяется **раньше** лимита карты, поэтому отказ
  `account_credit_limit_exceeded` ничего не говорит об остатке карты.

## Валюты и конвертация

Карта расчётная в **USD**. Платёж в другой валюте конвертирует
платёжная сеть вместе с эмитентом; мы на это не влияем.

### Две пары полей

| Поле | Что это |
|---|---|
| `amount` / `currency` | **списано** — в валюте расчёта, USD |
| `localAmount` / `localCurrency` | **запрошено мерчантом** — в его валюте |

Приходят в `data` на каждом спенд-событии `transaction.*` и в чтении
транзакции.

### Курс не отдаётся

**Ни курса, ни отдельной комиссии за конвертацию в API нет.** Наценка
сети зашита в курс и отдельной строкой не видна.

Если нужно показать курс — выводим сами: `amount / localAmount`.
Подавать строго как расчётный, не как официальный курс.

### Сумма списания известна только при сеттлменте

Холд ставится по курсу на момент авторизации. Пока операция оседает,
курс уходит, и финальное списание отличается от холда. Это штатное
поведение, а не ошибка.

**Леджер ведём по сеттлменту, не по авторизации.** Авторизация —
только резерв доступного.

Курсовая разница — легальный путь в перерасход: лимит проверялся при
авторизации, а списание пришло выше. Дальше действуют правила
перерасхода из `docs/domain-and-money.md`.

### Как отличить курсовую разницу от чаевых

Если `localAmount` завершённой операции **равен** `localAmount`
последней авторизации (`transaction.created` или более позднего
`transaction.updated`, изменившего холд), то мерчант запросил ту же
сумму в своей валюте, и разница в USD — курс.

Если `localAmount` **вырос** — это доплата: чаевые, доп. услуги.

После частичного реверса базовой линии нет, способ не работает.

### ⚠️ Сумму авторизации надо сохранять из события

Чтение `GET /transactions/:id` **переписывает `authorizedAmount` на
фактически списанную сумму**. Событие — нет.

Значит, полагаясь только на чтение, исходную сумму авторизации мы
теряем навсегда и отличить курс от чаевых уже не сможем.

**Сохранять `authorizedAmount` и `localAmount` из `transaction.created`
в момент получения события.** Задним числом не восстановить.

### ⚠️ Три разные конвенции единиц

На этом легко словить ошибку в 100 раз.

| Где | Формат |
|---|---|
| `amount`, `localAmount` в событиях | целые сотые доли валюты — **включая JPY** |
| `amount` в `challenge.requested` | минорные единицы ISO 4217 (у JPY — целые йены) |
| суммы в симуляторе | мажорные единицы, для всех валют включая JPY |

Для валют без дробной части (JPY) одно и то же число в разных местах
API отличается в сто раз. **Проверить на песочнице до продакшна.**

### Прочее

- Частичный реверс: `transaction.updated` приходит с `localAmount: 0`
  в `usd` — валюту мерчанта брать из других событий или из чтения.
- Валюты, подтверждённые в симуляторе: EUR, GBP, JPY, CAD, AUD, CHF,
  SGD, HKD. Прочие добавляются по запросу. В проде карта примет всё,
  что примет сеть.
- На update, settle, refund и reverse поле `currency` необязательно и
  игнорируется: эмитент читает суммы в валюте авторизации, а частичный
  реверс — в USD.
- 3-D Secure челленджи всегда в USD.
- **Возврат идёт по курсу возврата, а не покупки.** Пользователь может
  получить назад меньше потраченного. Частый повод для обращения —
  показывать обе суммы.

## Режимы работы адаптера

`OXEN_MODE` в `.env`:

- `mock` — локальная заглушка, реализующая контракт. Режим разработки
  до получения доступа.
- `sandbox` — реальный sandbox Oxen.
- `production` — боевой.

Заглушка должна уметь воспроизводить **неприятные** сценарии, а не
только счастливый путь: задержку KYB, `429`, `401` от троттлинга,
`502 PROVIDER_AMBIGUOUS`, потерю вебхука, перерасход, отказ по пулу.

Контрактные тесты пишутся против интерфейса адаптера и гоняются на
обоих режимах. Переключение `mock` → `sandbox` — **отдельный этап
работ**, не полдня: расхождения будут.

## Комиссии Oxen

В API нет ни одного поля про стоимость выпуска карты — ни в запросе,
ни в ответе, ни в ошибках. Это не значит, что выпуск бесплатный:
значит, что через наши вызовы плата не проходит.

Два места, где комиссии в их API есть:

- **Депозиты в пул** несут `fee` и `net` рядом с `gross`. Механизм
  удержания встроен; ненулевая ставка или нулевая — вопрос договора.
- **Диспуты** от 30 USD несут комиссию независимо от исхода. Менее
  30 USD не подаются в сеть и не тарифицируются.

**Что проверить на песочнице (этап 8).** Если плата за выпуск
списывается из пула, он будет уменьшаться без видимой причины, и
расчёт покрытия на дашборде этого не объяснит.

Проверка: прочитать остаток пула → выпустить карту → прочитать
остаток снова. Изменился — плата идёт из пула, и её надо отражать
отдельной проводкой, а не списывать на расхождение сверки.

## Открытые вопросы к Oxen

Зафиксированы, ответы вносить сюда:

- Допустима ли расшифровка реквизитов на клиенте (подтвердить схему).
- **Платный ли выпуск карты и откуда списывается плата** — из пула
  или по договору. Замеряем сами на песочнице.
- Ставка комиссии на депозиты в пул.
- Поддерживается ли добавление карт в Apple Wallet и Google Wallet,
  и как при этом подтверждается владелец.
- **Есть ли верхняя граница значения накопительного лимита.** Потолок
  карты растёт всю её жизнь: он равен сумме всех пополнений, потому что
  счётчик потраченного не сбрасывается. Если у значения есть максимум,
  долгоживущая карта в него упрётся, и надо знать заранее — лечится это
  выпуском новой карты, а не правкой расчёта
  (`docs/domain-and-money.md`, «Почему потолок только растёт»).
- Конкретные цифры рейт-лимитов.
- Чек-лист go-live.
- Канал и SLA поддержки по инцидентам.
