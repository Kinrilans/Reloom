## Клиентская часть

**Вход: три способа вместо привязки по коду.**
Telegram (кнопка сразу открывает бота), почта с паролем, ключ доступа
для заведённых оператором. Из браузера проверить наличие Telegram
нельзя — привязку делает бот. Изнутри Mini App экран выбора не
показывается: Telegram сам сообщает, кто пришёл.
→ `docs/flows-user.md` (раздел уже переписан), `docs/states-user.md`
(коды состояний для новых экранов ещё не заведены).

**Почта и пароль в настройках.** Почта с отметкой «подтверждена», смена
через код на новый адрес; пароль для входа вне Telegram, у аккаунта из
бота его может не быть вовсе.

**Второй фактор** — приложение-аутентификатор или код на почту.
Отключение только через поддержку.

**Вкладка «Уведомления»** — тот же поток, что в боте, лентой. 3DS-код
дублируется туда: без Telegram взять его больше негде.

**Пополнение: сначала монета, потом сеть.** Пара «монета + сеть»
неразрывна, перевод не той монетой теряется так же, как перевод не
в той сети.

**Адрес создаёт пользователь.** Экран пополнения начинается с кнопки
«Создать адрес»: готового адреса нет, он заводится по запросу и
закрепляется за человеком. Уничтоженный после возврата адрес приводит
на тот же экран — пополнять по нему нельзя.

**Возврат по непрошедшей проверке.** Уведомление в ленте с кнопкой,
отдельный экран: сколько пришло, комиссия сети, сколько вернётся,
адрес отправителя без возможности его изменить. После отправки —
адрес уничтожен, предложение завести новый.

**Шага «я отправил» больше нет.** Транзакцию на адрес система видит
сама и сама же берёт ссылку на неё в историю. Экран «Подтверждение
перевода» и экран «Заявка на проверке» остаются только для ручного
режима — когда автозачисление выключено в админке.
→ `docs/flows-user.md`, `docs/states-user.md` (Б-14 и Б-16 теперь
состояния ручного режима).

**«Активные транзакции» на главной.** Пока поступление идёт, над
историей операций висит акцентная кнопка со счётчиком; по ней снизу
выезжает шторка. Сначала список строк («Пополнение USDT» и точка
состояния цветом), подробности — по нажатию: три шага (подтверждения
сети, проверка происхождения, зачисление). Если проверка не пройдена —
тут же кнопка возврата. Нужно, чтобы между «отправил» и «зачислено»
человек не оставался без ответа.

Точка состояния идёт без подписи, но состояние названо словами внутри
и лежит в `aria-label`: цветом одним состояние не передаётся
(`docs/prototype.md`).
**Проверить по API сервиса адресов:** отдаёт ли он число подтверждений
и события по входящим транзакциям, или их придётся дотягивать с нод.

**Калькулятор пополнения вместо фиксированного расчёта.** Сумму
выбирает человек, и «переведёте 500» на экране адреса было выдумкой.
Теперь показываются ставка, минимальная сумма и прикидка по готовым
суммам. Живой пересчёт произвольной суммы — этап 1: считать комиссию
в прототипе нельзя (правило 3f).

**Смена пароля переехала** из отдельной карточки в блок «Безопасность»,
строкой рядом со сменой PIN.

**3DS: канал доставки под вопросом.** См. `docs/open-decisions.md`,
п. 16. До ответа Oxen сценарий 3DS не трогаем.

**Шапки на вкладках нет**, «глазик» переехал в строку счёта.

**PWA**: манифест и `viewport-fit: cover` — приложение добавляют на
рабочий стол и запускают без адресной строки.

## Админка

**Автоматическое зачисление системой.** Переключатель рядом с
комиссиями, меняется правом на комиссии (`MANAGE_SETTINGS`). Рядом —
порог риска AML и число подтверждений сети. Выключенный переключатель
возвращает прежний порядок: поступление ждёт оператора. Очередь заявок
остаётся в обоих режимах: в неё падает всё, что система зачислить
не смогла.
→ `docs/flows-admin.md`, `docs/domain-and-money.md` (расчёт зачисления
появляется на этапе 1, вместе с леджером и тестами).

**Адреса оператора заменены на адреса пользователей.** Общий адрес «на
всех» не позволяет отличить отправителя, а значит и зачислить без
человека. Теперь адрес заводит себе пользователь, адрес закреплён за
ним, и по поступлению система знает, чей это платёж. В разделе «Сети и
монеты» остались пары «сеть + монета», значок и минимальная сумма;
выданные адреса — в новом разделе «Крипто-адреса».
→ `docs/flows-admin.md`, `docs/flows-user.md` (на стороне пользователя
экран пополнения ещё не переделан под «создать адрес» — следующий шаг).

**AML-проверка поступлений.** После зачисления на адрес поступление
проверяется; оценка риска приходит от внешнего сервиса, мы её не
считаем — только сравниваем с порогом. Не прошло — деньги удерживаются
(статус `HELD`), зачисления не происходит.

**Возврат по непрошедшему AML — запускает пользователь.** Вопрос снят:
правило «деньги наружу — через оператора» здесь не нарушается, потому
что средства в систему не зачислялись. Они лежат на крипто-адресе,
в леджере их нет, получатель ровно один — адрес отправителя, и выбирать
не из чего. Команду отдаёт сервис кошелька, он же удерживает комиссию
сети; наша комиссия не берётся. Как только система видит, что средства
ушли, адрес уничтожается и больше не используется.

Оператору кнопка возврата оставлена на случай, когда пользователь
не отвечает, а деньги висят на адресе. Если это лишнее — уберём.
→ `docs/flows-user.md`, `docs/flows-admin.md`, `docs/open-decisions.md`
(п. 6 уже обновлён).

**Два новых внешних сервиса.**
- `new.cryptocurrencyapi.net` — выдача крипто-адресов и отправка
  возвратов;
- `getblock.net` — проверка AML.

Подключение — на этапе разработки: в прототипе нет ни бэкенда, ни
обращений наружу (`docs/prototype.md`). Сейчас сделаны экраны, фикстуры
и журнал обмена. **Ключи доступа в админку не выводятся** и в базе не
хранятся: переменные окружения (CLAUDE.md, правило 7). Оператор видит
только состояние сервисов в «Состоянии системы».
→ `docs/architecture.md`, `docs/security.md`, новый документ по
интеграции (по образцу `docs/oxen-integration.md`).

**Журнал обмена стал общим на три сервиса** — добавлены колонка и
фильтр «Сервис». Из «Состояния системы» в него ведут ссылки по
`requestId`: список проблем без перехода к самой проблеме заставляет
искать её руками.

**Дашборд: выручка первой строкой.** Прибыль с комиссий (с разбивкой
на пополнения и выводы) и сколько крипты пришло, по сетям. Разрез
берётся готовым под выбранную компанию — складывать разрезы в коде
нельзя, это те же деньги.

**«Пополнения» — это история, пока автозачисление включено.** Фильтр
по умолчанию «все», в списке и зачисленное, и удержанное, и заведённое
руками. При выключённом автозачислении экран снова становится очередью,
с предупреждением наверху.

**ВАЖНО для разработки: одну заявку не должны обработать дважды.**
В прототипе это пометка «заявку разбирает такой-то» на строке и в
карточке. На этапе разработки нужна настоящая защита, и она не в
интерфейсе:
- заявка **захватывается** оператором (claim) с отметкой кто и когда,
  захват протухает по таймауту;
- подтверждение и отклонение идут **идемпотентно**, по версии записи
  (optimistic lock): второй запрос по той же заявке не создаёт вторую
  проводку, а возвращает результат первого;
- переход статуса разрешён только из `SUBMITTED`; повтор из `CREDITED`
  отклоняется на сервере, а не кнопкой в интерфейсе.
→ `docs/flows-admin.md`, `docs/domain-and-money.md`.

**Поведение при недоступном AML — переключателем.** Рядом с
автозачислением: «зачислять, даже если проверка не ответила». По
умолчанию выключено, и это осознанно: сбой у стороннего сервиса не
должен превращаться в канал, по которому к нам заходит что угодно.
При включённом — на экране комиссий красное предупреждение.

**Заведение пользователя: три поля.** Компания, имя и почта. Телефон,
дата рождения и адрес убраны — эмитент соберёт их сам при проверке,
а набранное оператором по памяти придётся исправлять.

**Сети и монеты.** Список пар приходит от сервиса адресов (вместе со
значками, если он их отдаёт) — открывать сеть, в которой сервис не
выдаёт адрес, бессмысленно. Минимальная сумма получила собственный
переключатель: «ноль» и «минимума нет» — разные вещи. Карточки
в три ряда.
**Проверить по API:** отдаёт ли `new.cryptocurrencyapi.net` список
сетей и монет и их значки.

**Компания: поле депозитного адреса убрано.** Адрес выдаёт эмитент
после заведения и подтягивается сам; введённый руками означает пул,
ушедший на чужой кошелёк.

**Право `MANAGE_ADDRESSES`** теперь означает «уничтожать крипто-адреса
пользователей», а не «заводить адреса оператора».

**Аудит**: добавлены действия «переключение автозачисления»,
«уничтожение крипто-адреса», «возврат отправителю».

## Дизайн-система

- `Logo` — тон `duo` (фиолетовый знак, надпись цветом текста) вместо
  зелёного варианта; зелёный в интерфейсе не используется
  (`docs/brand.md` уже поправлен).
- `Button` — тройка `onBrand` / `onBrandSoft` / `onBrandGhost` для кнопок
  на фирменной заливке.
- `Amount` — маска вместо суммы, когда включён «глазик».
- `Select` — значок в строке списка.
- `Modal` и `Drawer` — починено закрытие: программное закрытие больше не
  досылает `onClose` наружу, иначе переход «первый шаг → второй» закрывал
  оба окна.
