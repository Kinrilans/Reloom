# Языки

Две поверхности, два набора языков, разные правила.

| Поверхность | Языки | По умолчанию |
|---|---|---|
| Админка | RU, EN | RU |
| Бот и Mini App | EN, RU, дальше расширяемо | **EN** |

**На время прототипа** язык по умолчанию везде русский — его смотрит
русскоязычное руководство (`docs/prototype.md`). Механика переводов
при этом строится как описано ниже. Перед разработкой дефолт
приложения возвращается на английский.

Язык добавляется файлом словаря, без изменений в коде. Архитектура
изначально рассчитана на N языков, а не на два.

---

## ГЛАВНОЕ ПРАВИЛО: хранить коды, а не текст

Ни одна строка, которую увидит человек, не хранится в базе на
конкретном языке. Хранится **код события и его параметры**;
в текст это превращается в момент показа, на языке читателя.

```
❌  notification.text = "Списание 49,99 $ в AMAZON"
✅  notification.code   = "spend.completed"
    notification.params = { amount: 4999, currency: "USD", merchant: "AMAZON" }
```

То же для: уведомлений, причин отказа, статусов, записей аудита,
ошибок, системных комментариев.

**Почему это не вкусовщина.** Пользователь меняет язык — вся его
история и все уведомления должны перечитываться на новом языке.
Оператор смотрит на то же событие по-русски, пока пользователь видит
его по-английски. Если текст уже вшит в базу, ничего из этого
не работает, и переделать потом — это миграция всех исторических
записей.

Исключение одно: **свободный текст, который написал человек** —
причина отклонения заявки от оператора. Он хранится как есть, вместе
с пометкой языка, на котором написан.

## Что переводится, а что нет

### Переводится
- Вся статика интерфейса: кнопки, подписи, заголовки, подсказки.
- Названия статусов: «На проверке», «Завершено», «Отклонено».
- Причины отказа по карте — у них ограниченный набор кодов от Oxen,
  каждому соответствует своя строка в словаре.
- Тексты состояний из `docs/states-user.md`.
- Письма и уведомления.

### Не переводится никогда
- **Название мерчанта.** Приходит от Oxen сырым (`SQ *COFFEE SHOP
  4411`) и показывается как есть. Машинный перевод названия магазина
  даст мусор и сделает операцию неузнаваемой.
- **Адреса кошельков, хеши, ссылки на транзакции.**
- **Названия сетей и монет** — «Tron (TRC-20)», «USDT».
- **Имя пользователя** в том написании, в котором его завели.

### Данные от Oxen — только английские
Это ограничение, а не выбор. Oxen отдаёт всё на английском:
статусы, коды ошибок, причины отказа, названия мерчантов.

Из этого следует: **мы переводим не данные, а их интерпретацию.**
Код `insufficient_funds` превращается в «Недостаточно средств» или
«Insufficient funds» через наш словарь. Сам код в базе остаётся
английским.

Неизвестный код, которого нет в словаре, показываем нейтральной
формулировкой («Операция отклонена»), а сам код пишем в лог для
оператора. Не показывать человеку сырой код и не падать на нём.

## Про автоперевод — осторожно

Машинный перевод в интерфейсе, где речь о деньгах, опасен: ошибка
в формулировке отказа или в описании операции порождает не непонимание,
а обращение в поддержку или неверное действие.

**Статику переводим вручную, словарями.** Строк немного, они меняются
редко, цена ошибки высокая. Автоперевод интерфейса не используем.

**Единственное оправданное место для автоперевода** — свободный текст,
который оператор написал по-русски, а читает его англоязычный
пользователь: причина отклонения заявки.

Если делаем, то так:
- оригинал сохраняется всегда и доступен;
- перевод помечен как машинный: «Переведено автоматически»;
- при недоступности переводчика показывается оригинал, а не пустота.

**Альтернатива проще и надёжнее:** набор готовых причин отклонения
(«Платёж не найден», «Сумма не совпадает», «Нет ссылки на транзакцию»,
«Другое») — они переводятся как обычная статика. Свободное поле
остаётся для редких случаев, туда и идёт автоперевод.

Рекомендую начать со списка причин, автоперевод добавить потом,
если понадобится.

## Выбор языка

### Пользователь
1. Язык, выбранный им в настройках — приоритет.
2. Если не выбирал — `language_code` из Telegram `initData`.
3. Если язык не поддерживается — **английский**.

Русский подставляется только при явном `ru`. Для всех остальных —
английский, это дефолт продукта.

Язык меняется в настройках и применяется ко всему сразу: интерфейсу,
уведомлениям, истории.

### Оператор
Язык в профиле оператора. По умолчанию русский.
Переключатель — в профиле, который открывается по имени оператора
в боковой панели. В шапке его нет: язык настраивают один раз, а место
рядом с выбором компании занимала настройка, которую переключают
по десять раз на дню.

### Уведомления
Отправляются на языке **получателя в момент отправки**, не на языке
того, кто спровоцировал событие. Оператор подтвердил зачисление
в русской админке — англоязычный пользователь получает уведомление
по-английски.

## Форматы

**Деньги.** Формат одинаковый во всех языках, чтобы сумму нельзя было
прочитать двояко: разделитель разрядов — узкий пробел, десятичный —
точка, код валюты после числа. `1 234.56 USD`.

Не локализовать разделители: `1,234.56` и `1.234,56` — это одно и то
же число, прочитанное противоположно, и в финансовом интерфейсе такой
риск не нужен.

**Даты и время.** В часовом поясе читателя, с явным указанием пояса
там, где это важно (сроки, карантин, обратный отсчёт). Формат
локализованный.

Разметку рисует сервер, а оживляет её браузер, и текст обязан совпасть
до символа. Пояс у них разный: сервер живёт в UTC, читатель где угодно.
Поэтому первая отрисовка идёт в UTC, а на пояс читателя переключается
сразу после гидратации. Иначе расхождение в один час рушит гидратацию
всей страницы.

**Числа и склонения.** Правила множественного числа разные: в русском
три формы, в английском две. Использовать plural-правила библиотеки,
а не собственные `if`.

Не склеивать строки из кусков — в разных языках порядок слов разный.
Только шаблоны с подстановкой: `«{count} операций на {amount}»`.

## Реализация

- Словари — JSON по языкам, плоские ключи по разделам:
  `user.card.freeze.title`.
- Отсутствующий ключ → фоллбэк на английский + запись в лог.
  Никогда не показывать сырой ключ.
- Один общий модуль перевода для админки, бота и Mini App — словари
  разные, механизм один.
- Тексты бота и Mini App берутся из одного словаря: пользователь
  не должен видеть разные формулировки одного и того же в чате и
  в приложении.
- Покрыть тестом: все ключи, используемые в коде, существуют во всех
  словарях. Отсутствие ключа в одном языке — ошибка сборки, а не
  сюрприз в продакшне.

## Что это добавляет к модели данных

```prisma
model User {
  // …
  locale  String  @default("en")   // en | ru
}

model Operator {
  // …
  locale  String  @default("ru")
}

model DepositRequest {
  // …
  rejectReasonCode String?   // из фиксированного списка
  rejectReasonText String?   // свободный текст оператора
  rejectReasonLang String?   // язык свободного текста
}
```

Уведомления и записи аудита хранят `code` + `params` (JSON),
не готовый текст.
