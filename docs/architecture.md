# Архитектура

## Принцип

Один монолит на TypeScript, одна база Postgres, минимум движущихся
частей. Никаких микросервисов, Kafka, Redis, отдельных очередей.
Команда — один человек плюс Claude Code; сложность инфраструктуры
убивает сроки и надёжность одновременно.

Масштаб задачи это позволяет: сотни пользователей, тысячи транзакций
в день — для Postgres это ничто.

## Процессы

Два запускаемых процесса:

**`web`** — Next.js: админка, Mini App, API-роуты, приём вебхуков.

**`worker`** — фоновые задачи:
- догон событий `GET /events` по курсору (постоянно)
- обработка очереди событий из `OxenEvent`
- outbox: отложенные вызовы Oxen с ретраями по allow-list
- **поступления на крипто-адреса**: подтверждения сети, запуск
  проверки происхождения, зачисление, отметка ушедшего возврата
  и уничтожение адреса
- периодическая сверка: пул, лимиты, инвариант платёжеспособности
- Telegram-бот

Разделение нужно, потому что веб-процесс может быть перезапущен или
отмасштабирован, а догон событий должен идти ровно в одном экземпляре.

## Слои

```
app/          UI и HTTP. Без бизнес-логики.
server/
  services/   бизнес-логика. Здесь всё важное.
  ledger/     проводки, балансы, инварианты. Отдельно от всего.
  oxen/       адаптер эмитента. Единственная точка контакта.
  wallet/     адаптер сервиса крипто-адресов и возвратов.
  aml/        адаптер проверки происхождения средств.
  db/         доступ к данным.
shared/       типы и хелперы, общие для сервера и клиента.
```

Правила зависимостей:
- `app` → `services` → `ledger` / `oxen` / `wallet` / `aml` / `db`
- `ledger` не знает ни про Oxen, ни про кошелёк, ни про проверку.
  Вообще.
- адаптеры не знают про наши доменные модели — возвращают свои типы,
  маппинг происходит в `services`.
- Обратных зависимостей нет.

Адаптеров три, и правило у них одно: **никто не ходит в чужой HTTP
напрямую**. API любого из них может поменяться ломающим образом, и
адаптер — единственный буфер.

## Ключевые паттерны

### Outbox для вызовов Oxen

Любой вызов, меняющий состояние в Oxen, сначала записывается намерением
в БД (вместе с идемпотентным ключом), и только потом исполняется.

Зачем: если процесс упадёт между «отправили запрос» и «получили ответ»,
мы должны знать, что карта могла быть выпущена, и не выпустить вторую.

### Событие → перечитать → применить

Событие Oxen никогда не является источником истины. Оно сообщает,
что изменилось. Действуем так:

1. Записали событие (дедуп по `evt_…`).
2. Перечитали ресурс через REST.
3. Применили изменения в нашей модели одной транзакцией БД.
4. Отметили событие обработанным.

Обработка идемпотентна: повторное применение того же события ничего
не меняет.

### Блокировки на уровне ресурса

Изменение лимита карты, зачисление пользователю, выпуск карты — под
блокировкой по ключу ресурса (`SELECT ... FOR UPDATE` или advisory lock).
Oxen отказывает при конкурентном изменении лимита, но полагаться на
его отказ нельзя — наши инварианты должны держаться сами.

### Глобальный троттлинг исходящих

Все исходящие запросы к Oxen идут через один ограничитель скорости,
потому что их рейт-лимит общий на всю платформу и превышение выглядит
как `401`.

## Аутентификация

**Админка** — вход по email и паролю плюс TOTP. Сессии в БД.
Без публичной регистрации; операторы заводятся вручную.

Права операторов разграничены (`MANAGE_USERS`, `APPROVE_DEPOSITS`,
`WITHDRAW`, `ADJUST_BALANCE`, `MANAGE_SETTINGS`, `MANAGE_ADDRESSES`,
`GRANT_RIGHTS`). Проверка прав — на сервере, в сервисном слое, а не
только в UI. Главный администратор единственный изначально имеет
`GRANT_RIGHTS`.

**Пользователь** — три способа входа, права у всех одинаковые:

- **Mini App.** `initData` от Telegram, сервер проверяет его HMAC по
  токену бота. Пароль не нужен.
- **Почта и пароль.** Для тех, у кого Telegram нет, и для работы
  с компьютера. Почта подтверждается обязательно: на неё уходит
  восстановление доступа.
- **Ключ доступа.** Одноразовый код привязки для заведённых
  оператором.

Проверить из браузера, есть ли у человека Telegram, нельзя — привязку
делает бот. Поэтому кнопка «через Telegram» просто открывает бота.

**Второй фактор** — приложение-аутентификатор или код на почту.
Отключается только через поддержку: самостоятельное отключение сводит
защиту к одному паролю ровно тогда, когда она нужнее всего.

**PIN приложения** спрашивается на чувствительные действия: реквизиты
карты, изменение лимита, запрос на возврат. Обоснование —
`docs/security.md`.

## Конфигурация

Всё через переменные окружения, перечень — в `SETUP.md` и
`.env.example`. Секреты в код не попадают. `.env` в `.gitignore`.

Переключение окружений Oxen — через `OXEN_MODE`, без изменения кода.

**Ключи внешних сервисов** — эмитента, сервиса адресов, проверки
происхождения — живут только в переменных окружения. В базе их нет,
в админку они не выводятся: оператор видит лишь состояние сервиса
в «Состоянии системы» (CLAUDE.md, правило 7; `docs/security.md`).

## Наблюдаемость

Минимум, но обязательный:

- Структурированные логи. В каждом логе вызова Oxen — `requestId`.
- **Никогда не логировать**: PAN, CVV, PIN, коды восстановления,
  API-ключи, `initData`.
- Журнал аудита на каждое действие оператора, двигающее деньги.
- Экран состояния в админке: отставание догона событий, необработанные
  события, нарушения инварианта, застрявшие вызовы Oxen.

## Что отложено

Сознательно не делаем на старте, но модель данных это допускает:

- Автоматический приём криптовалюты, курсы, обмен.
- Категоризация и очистка названий мерчантов.
- Физические карты, диспуты, bulk shipping.
