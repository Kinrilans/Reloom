# SETUP.md — установка окружения

Инструкция для человека без опыта разработки. Делать по порядку,
каждый шаг заканчивается проверкой.

---

## Что ставим и зачем

| Что | Зачем |
|---|---|
| Node.js 22 LTS | среда, в которой работает весь наш код |
| pnpm | менеджер пакетов (ставит библиотеки) |
| Docker Desktop | база данных PostgreSQL локально, без ручной установки |
| Git | уже подключён |

Редактор ставить не обязательно — Claude Code работает сам.

---

## Шаг 1. Node.js

**macOS / Windows:** скачать LTS-версию с https://nodejs.org и установить
обычным установщиком. Соглашаться со всем по умолчанию.

Проверка — открыть терминал и выполнить:

```bash
node --version
```

Должно напечатать `v22.` и дальше цифры. Если команда не найдена —
перезапустить терминал.

---

## Шаг 2. pnpm

```bash
npm install -g pnpm
```

Проверка:

```bash
pnpm --version
```

---

## Шаг 3. Docker Desktop

Скачать с https://www.docker.com/products/docker-desktop и установить.

После установки **запустить приложение** — в трее (Windows) или в
строке меню (macOS) должен появиться значок кита. Он должен быть
активен, иначе база не поднимется.

Проверка:

```bash
docker --version
```

> На Windows при первом запуске Docker может попросить включить WSL2 и
> перезагрузиться. Это нормально, соглашаемся.

## Шаг 4. Папка проекта

Распаковать архив в папку проекта. Внутри должны оказаться `README.md`,
`CLAUDE.md`, `SETUP.md`, `PROMPTS.md`, `.gitignore` и папка `docs/`.

Открыть эту папку в Claude Code: в десктопном приложении добавить её
через «+» рядом с полем ввода.

Сразу сделать первый коммит — чтобы документация была в git до того,
как появится код:

```bash
git init
git add -A
git commit -m "Документация проекта"
```

## Шаг 6. Переменные окружения

В корне проекта будет файл `.env.example` — это шаблон.
Скопировать его в `.env` и заполнить:

```bash
cp .env.example .env
```

Что заполнять:

| Переменная | Откуда взять |
|---|---|
| `DATABASE_URL` | оставить как в шаблоне (локальная база) |
| `OXEN_API_KEY` | sandbox-ключ от Oxen |
| `OXEN_BASE_URL` | `https://api.sbx.oxen.finance/v1/card` |
| `OXEN_RSA_PUBLIC_KEY` | публичный ключ от Oxen (для реквизитов карт) |
| `OXEN_WEBHOOK_SECRET` | секрет для проверки подписи вебхуков |
| `OXEN_MODE` | `mock` на старте, потом `sandbox`, потом `production` |
| `WALLET_API_KEY` | ключ от new.cryptocurrencyapi.net |
| `WALLET_WEBHOOK_SECRET` | секрет для проверки их вебхуков |
| `WALLET_MODE` | `mock` на старте |
| `AML_API_KEY` | ключ от getblock.net |
| `AML_MODE` | `mock` на старте |
| `TELEGRAM_BOT_TOKEN` | от @BotFather в Telegram |
| `ADMIN_SESSION_SECRET` | сгенерировать: `openssl rand -hex 32` |

**`WALLET_API_KEY` опаснее остальных:** им отправляют деньги с
крипто-адресов. Не пересылать его в мессенджерах и не показывать
на экране при демонстрациях.

**`.env` никогда не коммитится в git.** Он должен быть в `.gitignore`.
Если случайно закоммитил ключ — ключ считается скомпрометированным,
надо просить у Oxen новый.

Пока ключей нет — ставим `OXEN_MODE=mock` и работаем против заглушки.

## Шаг 7. Запуск базы данных

```bash
docker compose up -d
```

Поднимет PostgreSQL в фоне. Проверка:

```bash
docker compose ps
```

Должна быть строка со статусом `running (healthy)`. Пока написано
`health: starting`, база ещё не готова принимать подключения — подождать
несколько секунд.

Проверить, что мы в неё попадаем:

```bash
pnpm db:check
```

Остановить базу (данные сохранятся):

```bash
docker compose down
```

> **Если видно «port is already allocated» или ошибку авторизации.**
> Значит, порт занят другим Postgres, уже установленным на компьютере.
> Поменять `POSTGRES_PORT` в `.env` на свободный (5435, 5436…) и ровно
> на столько же поправить порт в `DATABASE_URL`.

## Шаг 9. Первый оператор

В админку нельзя зарегистрироваться: операторов заводит другой
оператор. Самого первого — главного администратора — создаёт команда:

```bash
pnpm db:seed-admin admin@example.com
```

Она напечатает **одноразовый пароль**. Он показывается один раз: в базе
лежит только его хэш. Если пароль потерян, команду можно выполнить
ещё раз с той же почтой — она выдаст новый, а не заведёт второго
оператора.

Второй фактор администратор подключает сам при первом входе: экран
входа покажет секрет, который надо ввести в приложение-аутентификатор
(Google Authenticator, 1Password, любой другой). Без второго фактора
войти нельзя — админка двигает чужие деньги.

## Шаг 10. Запуск

```bash
pnpm dev
```

Админка откроется на http://localhost:3000/admin

Фоновые процессы — отдельной командой. Без них не идёт догон событий,
а значит в админке не появятся траты по картам:

```bash
pnpm dev:worker
```

## Повседневные команды

Тесты ходят в базу: ядро системы — леджер, а он весь про транзакции,
уникальные индексы и одновременную работу двух операторов. Перед
`pnpm test` нужен `docker compose up -d`, как и перед `pnpm dev`.

**База у тестов своя — `reloom_test`, отдельная от рабочей.** Каждый
случай начинается с полной очистки таблиц, поэтому рабочую базу им
давать нельзя: один прогон стирает всё, включая оператора админки.
Создаёт и обновляет её `pnpm db:test-prepare`, который запускается сам
перед тестами; адрес берётся из `TEST_DATABASE_URL` в `.env`. Если
переменной нет или она совпадает с `DATABASE_URL`, тесты не стартуют
вовсе.

```bash
pnpm dev              # запустить админку и приложение
pnpm dev:worker       # запустить бота и фоновые процессы
pnpm test             # прогнать тесты (нужна поднятая база)
pnpm typecheck        # проверить типы
pnpm db:check         # проверить, что база отвечает
pnpm db:migrate       # применить изменения модели данных
pnpm db:seed-admin    # создать первого оператора или выдать ему новый пароль
pnpm db:test-prepare  # создать и обновить отдельную базу для тестов
pnpm db:generate      # пересобрать клиент базы после правки схемы
pnpm prisma studio    # посмотреть содержимое базы в браузере
docker compose up -d  # поднять базу
docker compose down   # остановить базу
```

## Если что-то сломалось

Порядок действий, прежде чем звать на помощь:

1. Скопировать **полный** текст ошибки.
2. Проверить, запущен ли Docker Desktop.
3. Проверить, что база поднята: `docker compose ps`.
4. Отдать текст ошибки Claude Code целиком, не пересказывая.

Чего не делать: не удалять папку проекта, не чинить вручную файлы в
`node_modules`, не делать `git push --force`.

## Про git

Коммитить часто, маленькими шагами, после каждого работающего куска.
Перед рискованными изменениями — отдельная ветка.

```bash
git add -A
git commit -m "что сделано"
git push
```

Никогда не коммитить: `.env`, ключи, дампы базы, скриншоты с реквизитами карт.
